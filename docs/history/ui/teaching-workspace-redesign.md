# Edu-Agent Teaching Workspace 产品重构设计

> 状态：DESIGN ONLY。本文件只定义产品方向，不修改数据库、API、UI、Migration 或现有业务语义。
>
> 设计基线：Phase 1–7A 当前实现；重点参考现有 `Lesson`、`TeachingPlan`、`Evidence`、`LessonDelivery`、`Reflection`、`TaskWorkingSet`、`ContextManifest`、Versioned Skill 与教师偏好能力。

## 1. 产品结论

Teaching Workspace 不应是“电子教案目录”，而应是围绕一节课持续工作的教学工作台。

它打开后首先回答四个问题：

1. 这节课现在处于哪个阶段？
2. 系统已经替教师完成了什么？
3. 还有哪一个决定必须由教师做？
4. 做完这个决定后，下一份可直接使用的成果是什么？

目标交互不是“进入重点难点、教学计划、课堂实施、课后反思分别填表”，而是：

```mermaid
flowchart LR
    L["选中课时"] --> I["系统准备教学洞察"]
    I --> D["教师确认教学意图"]
    D --> P["Agent 生成备课方案"]
    P --> A["教师采用或局部调整"]
    A --> M["系统生成教学材料"]
    M --> C["课堂后快速反馈"]
    C --> R["Agent 生成反思草稿"]
    R --> F["教师确认后续行动"]
    F --> N["下一课已带着证据开始"]
```

教师仍拥有最终控制权，但控制权表现为确认关键决策，而不是承担系统可以完成的文字录入。

## 2. 当前产品问题与必须保留的基础

### 2.1 当前问题

当前教学页已经拥有真实 API 和正式状态，但交互仍主要围绕对象分类：

- 顶层按课程、作业、考试划分；
- 课时内分别展示准备度、重点难点、作业、课堂实施、观察和反思；
- Lesson Delivery 要求逐环节填写实际实施文本、调整原因、节奏、问题和后续事项；
- Classroom Observation 仍以范围、类型、对象 Ref 和长文本为主；
- Reflection 虽可由 Agent 生成，但进入流程前仍需要教师理解多种对象和授权关系；
- Agent 入口存在，却没有持续表现为“本阶段已经替你做了什么”。

这套设计在数据治理上严谨，却把“可追溯”错误地转化成了“教师多填表”。

### 2.2 必须保留的正确语义

重构产品体验时必须保留：

- approved TeachingPlan 只是计划，不是课堂已经发生；
- Agent 输出只能是 Proposal 或 Draft；
- 教师确认的 Delivery / Observation 才能成为正式实施事实；
- Reflection 不覆盖原 TeachingPlan；
- confirmed Revision 不可原地修改；
- 后续备课、作业或 Todo 必须由教师显式创建；
- 每次 AgentRun 重新授权并封存 ContextManifest；
- 只允许教师明确选择的 Evidence 进入上下文；
- TeacherPreference 只能影响表达和组织，不能改变教育事实；
- 单次课堂现象不能生成长期学生能力标签。

产品重构的任务，是用更轻的交互实现同样严格的事实边界。

## 3. 产品北极星

### 3.1 核心价值

每次打开课时，教师都应看到一个“已经准备到这里”的工作现场，而不是一组等待填写的空栏目。

系统默认完成：

- 汇总课时、目标、当前 approved plan 和关联材料；
- 基于已授权来源生成教学洞察草稿；
- 标记重点、难点、常见错误和证据缺口；
- 生成少量可比较的教学方案；
- 按批准方案准备教案、练习、板书和课件大纲；
- 把课堂后的轻量反馈整理成 Delivery draft；
- 对比 planned / implemented 并生成 Reflection draft；
- 给出下一课、补充练习或个人 Todo 的候选行动。

教师主要负责：

- 确认或纠正教学意图；
- 选择方案；
- 对局部内容说一句修改要求；
- 确认课堂上真实发生了什么；
- 确认反思和后续行动。

### 3.2 交互预算

正常路径建议遵守以下产品指标：

| 环节 | 教师主动操作预算 | 长文本要求 |
|---|---:|---|
| 理解本课 | 30–60 秒，1–3 个确认 | 无 |
| 选择备课方案 | 2–3 分钟 | 可选一句话 |
| 准备材料 | 1–2 分钟确认成果 | 无 |
| 课后快速反馈 | 30–60 秒 | 可选语音/一句话 |
| 确认反思与后续 | 1–2 分钟 | 只改不准确处 |

Happy path 不出现必填空白长文本框。只有教师选择“补充说明”或“局部改写”时才出现输入框。

## 4. 教师真实工作流模型

### 4.1 阶段总览

| 阶段 | 教师做什么 | 系统做什么 | Agent 做什么 | 教师必须确认什么 | 正式结果 |
|---|---|---|---|---|---|
| 课时进入 | 打开今天或近期课时 | 恢复课时、计划、材料、任务和 Evidence 状态 | 判断当前阶段和下一项最有价值动作 | 无 | Lesson Journey 读取投影 |
| 看懂本课 | 浏览系统准备的洞察卡 | 汇总目标、教材范围、历史计划、已选 Evidence 和缺口 | 生成重点、难点、常见错误、班级关注点候选 | 哪些判断符合本班、哪些需要调整 | 教学意图/决策，不直接成为实施事实 |
| 形成方案 | 在 2–3 个方案中选择 | 展示与当前 approved plan 的差异和影响 | 生成教学流程、活动、提问、检查与备用路径 | 采用、局部修改、重新生成或暂不采用 | TeachingPlan draft / in-review / approved |
| 准备材料 | 预览并确认需要的成果 | 汇总文件版本和生成状态 | 按 approved Revision 生成教案、练习、板书、课件大纲候选 | 哪些材料可直接使用，哪些需局部重做 | FileAsset / FileVersion，与明确 Revision 绑定 |
| 课堂实施 | 正常上课；只记录异常和关键现象 | 默认以 approved plan 为比较基线 | 不自动声称课堂发生了什么 | 课后快速确认“基本按计划”或点选差异 | LessonDelivery draft → teacher confirmed |
| 课后反馈 | 点选达成度、节奏和显著现象 | 汇总课堂快速信号与作业 Evidence | 生成 planned vs implemented 和反思草稿 | 哪些现象是真实的、反思是否准确 | Observation / Reflection confirmed revisions |
| 下一课优化 | 选择一个或多个后续行动 | 保留来源关系并更新工作台 | 生成下一课调整、练习或 Todo 草稿 | 是否创建、采用和批准 | 新 Task / Assignment draft / Todo |

### 4.2 课时进入

教师通常不是为了“维护 Lesson”而打开系统。他可能来自：

- 今天的课程；
- 工作台上的“需要确认方案”；
- 作业分析中的“调整下一课”；
- 日历中的已结束课程；
- Agent 生成完成提醒；
- 文件中的教案或练习成果。

无论入口来自哪里，系统都恢复同一个 Lesson Journey，并将教师带到尚未完成的下一阶段，不要求重新寻找上下文。

### 4.3 看懂本课

系统先生成一页“本课教学简报”，而不是让教师填写重点和难点。

简报至少包含：

- 本课要解决的核心问题；
- LearningObjectives 与可观察的成功标准；
- 教学重点、难点和先备知识；
- 教材位置与前后课关系；
- 常见错误、易混概念和典型诊断题；
- 当前班级 Evidence 中与本课相关的信号；
- 当前未知项和来源不足；
- 与教师已确认偏好有关的呈现方式。

教师的默认操作是：

- “符合本班”；
- “这项需要加强”；
- “本课暂不处理”；
- “换一个切入点”；
- “补充一句”。

系统把这些选择转为教学意图和 Agent 约束，而不是让教师重新写一份分析。

### 4.4 形成备课方案

Agent 根据已确认教学意图生成少量明确方案，例如：

- 稳妥推进：概念澄清 → 示范 → 独立检查；
- 问题驱动：真实情境 → 学生猜想 → 归纳规则；
- 针对误区：错误样例 → 对比辨析 → 迁移练习。

每个方案只显示教师需要判断的差异：

- 为什么适合当前班级；
- 预计课堂节奏；
- 关键活动和检查点；
- 所依据的 Evidence；
- 不适用条件和已知缺口；
- 相对当前 approved plan 改了什么。

教师可以采用整套方案，也可以只替换一个环节。系统必须支持“保留其他部分，只重做课堂检查”这样的局部指令。

### 4.5 准备教学材料

TeachingPlan 被批准后，系统显示“本课材料包”，而不是让教师在文件页逐个寻找：

- 教案 DOCX；
- 课堂练习；
- 板书结构；
- 课件大纲；
- 参考资料；
- 备用活动或分层材料。

每个成果显示：

- 当前版本；
- 来源 TeachingPlan Revision；
- 是否已就绪；
- 最近生成/修改时间；
- 预览、下载、局部重做、进入文件库。

材料生成失败应在本阶段直接显示原因和重试入口，不要求教师到 Runs 页面理解普通失败。

### 4.6 课堂实施

课堂实施不应以“请填写每个环节实际内容”为开始。

系统在课后提供一张快速反馈卡，默认假设“尚未确认”，但预填 approved plan 的环节。教师只标记差异：

- 基本按计划完成；
- 某环节比预期更慢/更快；
- 某活动特别有效；
- 学生在某概念处卡住；
- 跳过某环节；
- 临时增加某环节；
- 需要下节课继续。

推荐两层反馈：

1. **15 秒快速反馈**：整体达成度 + 1–3 个差异标签；
2. **60 秒事实确认**：系统据此生成 Delivery draft，教师查看摘要后点击“与实际一致”。

只有第二步确认后才形成正式 LessonDelivery Revision。课程时间结束只能触发提醒，不能自动创建实施事实。

若教师确实需要补充，可使用一句话或语音，例如“例 2 花了 8 分钟，拓展题没做”。系统负责拆成节奏变化、跳过环节和后续事项候选，再由教师确认。

### 4.7 课后复盘

Agent 使用以下明确授权内容生成 Reflection draft：

- approved TeachingPlan Revision；
- confirmed LessonDelivery Revision；
- confirmed Classroom Observations；
- 教师选择的 Assignment Evidence；
- LearningObjectives；
- 教师可选的一句话补充。

反思页面首先显示三类结论：

- **本课发生了什么**：只复述已确认事实；
- **意味着什么**：基于 Evidence 的解释和未知项；
- **下一步做什么**：下一课、练习和待办候选。

教师通过“准确 / 需修改 / 不确定”快速审阅。只有不准确部分展开局部编辑。确认后形成 Reflection Revision，但不会自动修改 TeachingPlan 或创建任务。

### 4.8 下一课优化

Reflection 确认后，系统展示最多三项可执行候选：

- 调整下一课；
- 创建补充练习；
- 创建个人 Todo。

教师显式勾选后才创建对象。新 lesson preparation Task 的 TaskWorkingSet 应保存 Reflection、Delivery、Observation 和选定 Evidence 来源；下一次 AgentRun 再次授权并封存 ContextManifest。

## 5. Teaching Workspace 信息架构

### 5.1 从对象目录转为 Lesson Journey

教学工作区仍可保留 CourseRun → Unit → Lesson 导航，但选中课时后的主区域改为任务旅程：

```text
课时上下文
├── 当前阶段与唯一主操作
├── 1 看懂本课
├── 2 定下方案
├── 3 准备材料
├── 4 课堂反馈
└── 5 复盘与下一步
```

“重点难点、TeachingPlan、文件、课堂实施、Reflection”不再是同级栏目，而是各阶段的产物。

### 5.2 页面结构

#### A. 课时上下文条

固定显示：

- 课程、单元、课时；
- 上课时间；
- 当前班级；
- 当前阶段；
- approved plan / 材料 / 课堂反馈 / Reflection 的关键状态；
- 返回来源入口。

#### B. 下一步主卡

页面最显著区域只提供一个主操作，例如：

- “确认本课教学洞察”；
- “从 2 个方案中选择”；
- “审核教学计划”；
- “检查本课材料包”；
- “用 30 秒记录课堂反馈”；
- “确认课后复盘”；
- “本课已闭环，查看下一课”。

卡片同时说明：系统已经完成什么、为什么需要教师决定、预计耗时多久。

#### C. Lesson Journey

五个阶段纵向或横向排列。已完成阶段显示结果摘要，可展开查看；当前阶段默认展开；未来阶段只显示依赖条件，不展示空表单。

#### D. Agent 工作区

Agent 不表现为常驻聊天框，而表现为与当前阶段绑定的工作区：

- 已读取的上下文；
- 已完成的工作；
- 等待教师确认的决定；
- 缺失或被排除的信息；
- “告诉 Agent 一句话”的可选输入；
- 生成、局部重做、比较、解释来源。

#### E. 来源与历史抽屉

Evidence、ContextManifest、Revision history、Audit 和 Runs 保留，但默认折叠。教师需要追溯时可以查看，不占据日常路径。

### 5.3 页面状态规则

- 任何时刻最多一个 primary action；
- 不满足前置条件的阶段显示原因和解决入口；
- 系统生成中显示可离开页面、完成后提醒；
- 失败在当前业务语境中解释，不要求教师自行解读运行状态；
- 草稿、待确认、已批准、已实施和已反思使用稳定一致的状态语言；
- 不因为页面打开、时间到达或模型成功而自动推进正式状态。

## 6. 核心模块设计

### 6.1 教学洞察

#### 系统生成

- 课程标准关联；
- 教材分析和知识前后关系；
- 教学目标和成功标准；
- 重点、难点与先备知识；
- 考点或评价要求；
- 常见错误；
- 当前班级 Evidence 信号；
- 已知缺口。

#### 教师操作

- 确认整组洞察；
- 标记“加强 / 降低 / 暂不处理”；
- 替换建议切入点；
- 查看来源；
- 与 Agent 讨论一个具体判断；
- 用一句话补充班级情况。

#### 关键边界

当前仓库没有完整、权威的课程标准、教材知识体系和考点知识源。未来接入前：

- 模型不能被当作课程标准事实来源；
- 每项洞察必须显示 provenance、version 和适用范围；
- 无来源时明确显示“权威来源尚未接入”或“这是教学建议”；
- 班级分析只能使用教师明确授权的 Evidence；
- 低置信或冲突信息必须进入“待教师判断”，不能静默合并。

### 6.2 备课方案

#### 系统生成

- 2–3 个有清晰差异的教学路径；
- 教学流程与时间预算；
- 课堂活动和教师提问；
- 独立检查和诊断点；
- 针对当前 Evidence 的支持策略；
- 备用路径与已知风险；
- 与 current approved 的差异。

#### 教师操作

- 采用；
- 只采用某一环节；
- “保留其他部分，只修改……”；
- 重新生成指定部分；
- 提交审核；
- 单独批准。

#### 结果

Agent 只产生 Proposal 或 TeachingPlan draft。处置 Proposal、进入 in-review、批准 Revision 和显式完成备课仍是不同动作。

### 6.3 教学材料

#### 系统生成

- approved TeachingPlan DOCX；
- 练习草稿；
- 板书结构；
- 课件大纲；
- 分层支持材料；
- 与计划步骤对应的材料清单。

#### 教师操作

- 预览；
- 下载；
- 局部重做；
- 替换参考文件；
- 标记“本课使用”；
- 进入文件库查看位置和版本。

#### 关键边界

所有正式材料继续由 Artifact/File Application Service 创建。模型不能直接写 FileAsset 正式状态。每个版本必须绑定明确 TeachingPlan Revision，不使用含混的 latest。

### 6.4 课堂实施

#### 快速反馈设计

课堂结束后显示：

1. “整体是否基本按计划？”——是 / 有调整；
2. “学生在哪一步最需要帮助？”——从计划步骤和目标中选择；
3. “本节最明显的结果？”——达成 / 部分达成 / 未判断；
4. 可选异常标签——节奏慢、节奏快、活动有效、理解混淆、跳过、临时增加；
5. 可选一句话补充。

系统把反馈组织为 Delivery draft 和 Observation candidates。教师看到的是一段简明摘要，并通过“确认与实际一致”形成正式事实。

#### 不允许

- 不把默认预填内容直接确认为事实；
- 不因 CalendarEvent 结束自动创建 Delivery；
- 不让 Agent 自动确认 Observation；
- 不要求教师逐项复制 approved plan 文本；
- 不将一次课堂现象升级为长期学生标签。

### 6.5 课后反思

#### Agent 辅助复盘

Agent 自动回答：

- 哪些目标有 Evidence 支持；
- 实施与计划的关键差异；
- 哪些活动可能有效；
- 哪些判断仍缺 Evidence；
- 下一课最值得调整的一件事；
- 是否需要补充练习。

#### 教师操作

- 快速确认准确项；
- 标记不准确或不确定项；
- 对单项说一句修改要求；
- 确认 Reflection；
- 显式选择后续行动。

Reflection 的正式内容可以保留完整结构，但长文本应由系统生成，教师只编辑例外。

## 7. Agent 交互设计

### 7.1 Agent 的产品角色

Agent 是阶段感知的工作协作者，不是一个脱离业务对象的聊天页面。

每次出现都应具备：

- 明确 Purpose；
- 明确 Lesson / Task；
- 明确 SkillVersion；
- 明确授权资源；
- 明确将产生 Proposal、Draft 还是解释；
- 明确哪些动作仍需教师确认。

### 7.2 主动出现时机

| 时机 | Agent 可以主动做什么 | 不可以做什么 |
|---|---|---|
| 课时进入且洞察未准备 | 后台准备 Lesson Brief | 自动确认重点难点 |
| 新 Evidence 与当前课相关 | 提醒“班级信号有变化”，生成差异摘要 | 自动扩大到全班所有提交 |
| 教师确认教学意图 | 生成少量备课方案 | 自动批准计划 |
| TeachingPlan approved | 准备材料候选 | 自动声明材料已由教师采用 |
| 课程结束 | 提醒进行快速反馈 | 自动声称课程已实施 |
| 教师确认 Delivery/Observation | 生成 Reflection draft | 自动确认反思 |
| 教师确认 Reflection | 提供后续行动候选 | 自动创建全部任务 |

### 7.3 什么时候询问教师

Agent 只在以下情况打断教师：

- 两条可靠 Evidence 明显冲突；
- 缺少会实质改变方案的关键事实；
- 教师选择会改变正式计划或材料；
- 需要扩大 Context 范围或加入新的 Evidence；
- 生成结果包含低置信或无法验证的判断；
- 正式确认、发布或创建后续行动。

一般性的写作偏好、版式偏好和输出长度由已确认 TeacherPreference 自动应用，不重复询问。

### 7.4 什么时候等待

以下状态必须等待教师：

- Proposal 采用或拒绝；
- TeachingPlan approve；
- Delivery confirm；
- Observation confirm；
- Reflection confirm；
- Assignment publish；
- 后续 Task/Todo 创建；
- Context 权限扩大。

Runtime 的 `waiting_for_human` 应直接翻译成具体业务问题，而不是只显示技术状态。

### 7.5 一句话交互

“对 Agent 说一句话”应附着在具体对象和阶段上，例如：

- “导入不要用生活购物案例，换成温度变化。”
- “保留练习 1，第二题改成分层题。”
- “今天例 2 花太久了，拓展题没做。”
- “下一课先复习斜率和截距的区别。”

系统把句子转成结构化候选变更并展示 diff。原句本身不直接写入正式领域状态。

## 8. 数据模型影响评估

### 8.1 当前对象是否保留

| 对象 | 建议 | 原因 |
|---|---|---|
| Lesson | 保留 | 仍是教学旅程锚点，不应承载生成内容 |
| TeachingPlan / Revision | 保留并逐步结构化 | 正式计划、审批和历史语义正确；当前内容字段偏长文本 |
| Evidence | 保留 | 必须继续作为可追溯来源，不转成 UI 标签真值 |
| Reflection / Revision | 保留 | 独立于计划的正式复盘对象语义正确 |
| Task / TaskWorkingSet | 保留 | 负责目的、工作范围和显式后续关系；避免为每个页面卡片创建 Task |
| AgentRun / RunStep | 保留 | 继续记录执行、恢复、SkillVersion 和 ContextManifest |
| LessonDelivery / Observation | 保留 | 正式实施事实边界正确；输入方式需要轻量化 |
| TeacherPreference | 保留 | 只影响表达、材料组织和建议风格，不改变事实判断 |

### 8.2 建议增加的产品读取模型

以下是未来建议，不在本轮实现：

| 建议对象 | 性质 | 所有者建议 | 说明 |
|---|---|---|---|
| LessonJourneyProjection | 可重建读取模型 | Work | 汇总各源对象状态，给出当前阶段和 next best action，不成为真值 |
| LessonBriefSnapshot | 可版本化 Proposal/Artifact | Artifact | 保存洞察候选、来源版本、缺口和教师选择；不能冒充课程标准事实 |
| MaterialBundleProjection | 可重建读取模型 | Artifact | 汇总与明确 TeachingPlan Revision 绑定的文件成果 |
| ClassroomFeedbackSignal | 教师输入事件或 draft input | Education | 保存快速选择和一句话来源，用于生成 Delivery/Observation draft；未确认前不是正式事实 |
| AgentDecisionRequest | Runtime 输出摘要 | Runtime/Work projection | 把 waiting_for_human 翻译成教师可理解的单一决定 |

不建议创建万能 `TeachingWorkspace` 聚合表。页面由读取投影组合，正式状态仍由所属模块拥有。

### 8.3 TeachingPlan 内容建议

当前 TeachingPlan 以 `objective`、`lessonFocus`、`openingActivity`、`studentActivity`、`supportStrategy` 等文本字段为主。未来可通过新版本 Contract 演进为更可操作的结构：

- intent / success criteria；
- ordered plan segments；
- activity and question refs；
- checks for understanding；
- timing budget；
- contingencies；
- material refs；
- evidence rationale；
- known gaps。

旧 Revision 必须继续可解释，不能改写历史 Contract 或 Migration。

### 8.4 权威知识来源

要真正自动生成课程标准、教材分析和考点关联，需要未来建立受治理的知识来源边界：

- Education 保存课程标准、教材版本和知识节点的稳定引用；
- Capability 提供授权内容 Adapter；
- Context Builder 只取回当前学校、课程和版本允许使用的内容；
- ContextManifest 记录来源、版本、hash 和排除项；
- 模型只负责组织和建议，不作为规范事实的唯一来源。

在该边界建立前，产品应明确区分“权威内容”“班级 Evidence”“Agent 建议”。

## 9. 林老师完整一天 Demo 设计

Demo 使用匿名合成数据，但走正式 Session、PostgreSQL、Repository、Task、AgentRun、Artifact 和 Evidence 路径。

### 9.1 场景背景

- 教师：林老师；
- 课程：八年级 3 班数学；
- 当前课时：一次函数的应用；
- 下一课：一次函数图像与实际问题；
- 已有数据：LearningObjectives、上一份作业的 confirmed Evidence、教师已确认的“教案简洁、偏好案例导入”偏好；
- 所有课程标准/教材来源在 Demo 中必须标记为 synthetic reference content。

### 9.2 时间线

#### 07:30 — 打开工作台

系统显示：

- 08:30 上课；
- 本课洞察已准备；
- 只剩 1 个决定：“是否把斜率/截距混淆设为本课重点诊断项”；
- 预计需要 40 秒。

林老师点击“需要加强”，不填写长文本。

#### 07:32 — 选择方案

Agent 基于已授权 Evidence 给出两个方案：

- 案例导入 + 对比辨析；
- 错例诊断 + 分层练习。

林老师选择第一项，并说一句：“最后保留一道独立检查题。”

系统生成 diff，林老师提交审核并批准 TeachingPlan Revision。

#### 07:36 — 检查材料包

系统已准备：

- 教案 DOCX；
- 课堂练习；
- 板书结构；
- 课件大纲。

林老师预览练习，选择“第二题稍微简单一点”。Agent 只重做第二题；新 FileVersion 保留旧版本。

#### 08:30 — 上课

页面可提供简洁的计划查看和材料入口，但不做实时课堂监控，也不自动记录课堂事实。

#### 09:18 — 30 秒课堂反馈

林老师选择：

- 整体：部分达成；
- 活动：对比辨析有效；
- 节奏：例 2 超时；
- 未解决：部分学生仍混淆斜率和截距；
- 跳过：拓展题。

系统生成实施摘要。林老师点击“与实际一致”，形成 confirmed LessonDelivery；再确认一条班级范围 Observation。

#### 10:00 — Agent 完成复盘草稿

Reflection draft 显示：

- 基础目标基本达成；
- 对比辨析活动有正向课堂观察；
- 斜率/截距混淆仍存在；
- 拓展目标本节未验证；
- 建议下一课先做 5 分钟诊断，再进入图像应用。

林老师将“基本达成”改为“需要一次短诊断确认”，随后确认 Reflection。

#### 10:03 — 创建后续行动

林老师显式选择：

- 创建下一课备课 Task；
- 创建一份 3 题补充练习草稿；
- 不创建个人 Todo。

新 TaskWorkingSet 保存 Reflection、Delivery、Observation 和选定 Evidence 来源。Agent 不自动发布作业，也不自动批准下一课计划。

#### 17:00 — 回到工作台

工作台显示：

- 本课已完成计划—实施—反思闭环；
- 下一课备课方案等待确认；
- 补充练习仍是 draft；
- 所有状态刷新和重启后保持。

### 9.3 Demo 验收重点

- 林老师在 happy path 中没有填写任何必填长文本；
- 每个阶段只有一个主要下一步；
- Agent 的每次生成都有 Purpose、SkillVersion 和 ContextManifest；
- 计划、实施、观察和反思在页面上清楚区分；
- 课堂反馈没有被自动确认为事实；
- 后续行动由林老师显式创建；
- 所有成果可追溯到明确 Revision 和 Evidence；
- 服务重启后 Lesson Journey 恢复到同一阶段。

## 10. 成功指标

### 10.1 教师效率

- 从打开课时到 approved plan 的主动操作时间；
- Happy path 的必填文本框数量，目标为 0；
- 课后形成 confirmed Delivery 的中位时间，目标小于 60 秒；
- 生成材料后需要全文重做的比例；
- 从 Reflection 到下一课 Task 的完成时间。

### 10.2 教师控制与信任

- Proposal 局部修改率与拒绝率；
- 教师查看来源/缺口的比例；
- 系统建议被标记“不准确”的比例；
- 未确认内容进入正式状态的次数，目标为 0；
- 跨 tenant 或未授权 Evidence 使用次数，目标为 0；
- Preference 撤销后仍进入 Context 的次数，目标为 0。

### 10.3 教学闭环质量

- 有 approved plan 的课时中完成快速课堂反馈的比例；
- Reflection 中有明确 Evidence 来源或未知项的比例；
- 后续行动能够追溯到 Reflection/Observation/Evidence 的比例；
- 下一课方案明确回应上一课问题的比例。

## 11. 建议的后续产品实施顺序

本文件不授权实现。若未来进入开发，建议按风险递增拆分：

1. 先建立 LessonJourneyProjection 和单一 next action，不改变正式写入；
2. 将现有重点难点改为有来源的 Lesson Brief Proposal；
3. 在现有 Delivery/Observation API 前增加快速反馈生成草稿的交互层；
4. 将 Reflection 审阅改为“准确 / 修改 / 不确定”的局部确认；
5. 把材料按 TeachingPlan Revision 组成 Material Bundle；
6. 最后接入有版本、授权和许可的课程标准/教材知识源。

每一步都应保留旧状态的可解释性，并通过真实教师任务耗时验证，而不是只以页面完成度验收。

## 12. 五年后的回答

如果五年后 Edu-Agent 成为教师每天使用的系统，老师愿意每天打开它，不是因为里面保存了更多教案，而是因为：

- 它知道教师今天要上什么课、当前做到哪一步；
- 它已经完成了可以自动完成的分析、整理和初稿；
- 它只在真正需要专业判断时打断教师；
- 它把一句话和几个选择变成可用、可追溯的教学成果；
- 它记得教师明确确认的偏好，却不隐藏地定义教师或学生；
- 它能把上一课真实发生的问题带到下一课，而不要求教师重新录入；
- 它不会替教师批准、发布或虚构课堂事实；
- 它让教师每次打开系统都更接近“可以上课”，而不是更接近“又填完一张表”。

因此，Teaching Workspace 的最终产品承诺应是：

> **系统负责准备，教师负责判断；系统保存连续性，教师保留最终控制。**
