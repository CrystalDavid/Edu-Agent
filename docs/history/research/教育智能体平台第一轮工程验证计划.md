# 1. 本轮要验证的架构问题

本轮不以“页面数量”或“能否聊天”为成功标准，而验证以下问题：

1. 七模块在一个部署单元中能否保持清晰的数据所有权和依赖方向；
2. `Query → QueryRun` 与 `Command → Task → TaskRun` 是否足以承载短期智能执行；
3. `WorkflowInstance` 能否独立拥有等待和恢复状态；
4. `LearningInteractionProfile → ResolvedLearningInteractionContract` 是否能真正约束 Runtime；
5. Agent 能否使用 Evidence 提出有依据的建议，同时不把建议写成正式事实；
6. Opportunity、Attempt、Assistance 和 Evidence 的链条能否避免固化学生；
7. Personal Assistant Shell 是否能提供跨任务连续性而不持有权限和业务状态；
8. MemoryEntry 是否能改善任务体验，同时保持可审查、可删除和不越权；
9. Mock 模型、DeepSeek 模型和部署环境能否通过同一执行合约；
10. 一个首次使用的教师能否理解“系统使用了什么、为什么这样建议、我如何接管”。

# 2. 本轮范围

## 2.1 演示领域

推荐固定一个足够具体、又能覆盖核心对象的合成场景：

- 学段：八年级；
- 学科：数学；
- 单元：一次函数；
- 学习目标：理解斜率变化与图像特征的关系；
- 班级：一个合成班级；
- 学生：12 个匿名合成 Learner；
- 证据：两次合成作业、一次课堂练习、一次个别学习 Attempt；
- 教师：一个多角色合成教师；
- 长期对象：一个 CourseRun、一个 TeachingImprovementCase 和一个可独立存在的教师个人 Goal。

这不是对平台范围的永久限制，而是为了让第一轮的 Evidence、Opportunity、Attempt、TeachingPlan 和 Case 共享同一语境。

## 2.2 两个纵向切片

### Slice A：Teacher Copilot

```text
教师进入教学改进 Case
→ 查看 Goal 和班级 Evidence 摘要
→ 检查证据来源、时效、Assistance 和缺口
→ 发起“调整明天课堂”的 Query/Task
→ Runtime 按已解析互动契约生成 PedagogicalSuggestion
→ 形成 TeachingPlan Diff / OperationalProposal
→ 教师修改并选择接受、拒绝或延后
→ 系统记录 SuggestionDisposition、Artifact 版本和审计
```

不得在教师点击“接受”后自动创建 `ObservedPedagogicalMove`。

### Slice B：引导式个别学习

```text
合成学生进入 Goal 对应活动
→ 创建 individual 模式的 ResolvedLearningInteractionContract
→ 学生提交 Attempt
→ 系统按提示层级给出支持
→ 记录 AssistanceContext 和参与者归因
→ 确定性规则形成 Observation / Evidence 候选
→ 教师查看来源并确认或修正
→ LearnerStateEstimate 显示不确定性、时效和证据缺口
```

不得用一次 Attempt 形成固定能力标签；不得把 AI 帮助后的答案当作独立掌握。

## 2.3 非目标

- 真实学生、教师、家长或学校数据；
- 学校 SSO、教务同步和正式多租户运营；
- 心理健康推断；
- 自动对外发送消息；
- 多 Agent；
- 长期自主 Agent 进程；
- 自动生成并发布个人 Skill；
- 图数据库、向量数据库或微服务；
- 完整排课、考试、家校沟通和作业系统；
- 用一次演示证明学习效果。

# 3. 环境与部署策略

## 3.1 Local：所有工程验证的起点

本机必须可以在断开模型 API 时完成确定性闭环：

```text
Browser
→ Local Web
→ Local API
→ PostgreSQL
→ MockModelProvider
```

本地 PostgreSQL 优先使用 Docker；若环境不具备 Docker，则安装本机 PostgreSQL。不得为了省一步安装而让本地使用 SQLite、演示使用 PostgreSQL，从而制造双数据库语义。

本地环境需要：

- Git；
- 当前 LTS Node.js；
- pnpm；
- PostgreSQL 或 Docker；
- 一个未进入 Git 的 `.env.local`；
- Playwright 所需浏览器。

环境能力在编码前由自动化 preflight 检查，不要求用户手工判断版本。

## 3.2 Preview：先验证仓库与构建

```text
GitHub branch / PR
→ Netlify Deploy Preview
→ 合成数据
→ Mock 或受限 Demo API
```

Preview 用于验证：

- 前端构建；
- 路由刷新；
- 环境变量；
- API base URL；
- CORS；
- 移动/桌面基本布局；
- 回滚。

在 Preview 通过前，不改变现有 Netlify 生产站点的 Git 仓库关联。

2026-07-28 的只读检查显示，现有 URL 当前运行的是另一个应用 `PPT Agent v2026.6.1`，并非空白占位站。因此“关联新仓库”属于一次会替换现有应用的正式切换。切换前必须：

- 保留当前成功 Deploy 的可回滚引用；
- 记录现有构建设置和环境变量名称；
- 在独立 Preview 完成验收；
- 由用户明确确认该 PPT Agent 可以被教育智能体演示替换。

## 3.3 Demo：教师远程验收

推荐拓扑：

```text
Netlify
  Web
   │ HTTPS + demo token
   ▼
Tencent CloudBase HTTP Function
  Modular Monolith API + Worker
   │
   ├─ CloudBase PostgreSQL
   ├─ Object Storage（仅附件需要时）
   └─ DeepSeekProvider（服务端环境变量）
```

第一轮不创建腾讯云 CVM。只有 CloudBase Spike 证明函数环境不能满足演示所需的 API、数据库连接或运行恢复时，才重新提交部署 ADR；不能先买服务器再寻找理由。

## 3.4 密钥与外部服务

- 已经出现在对话中的 DeepSeek 密钥必须立即撤销并重新生成。
- 新密钥不得再次粘贴到聊天、代码、Markdown 或前端配置。
- 本机使用未跟踪的环境变量；云端使用 CloudBase Secret/环境变量。
- CI 和 Preview 默认使用 Mock，不需要真实密钥。
- 真实模型默认关闭，通过服务端 feature flag 和每日预算开启。
- Netlify 与 CloudBase 的访问授权在实际部署阶段再操作。


在 secret scan、测试和 Preview 通过前不向 `main` 合并。

## 4.2 模块结构

单一 API 部署中保留七个模块：

```text
src/modules/
  identity-governance-audit/
  work-assistant-durable-execution/
  agent-runtime-context/
  capability-integration/
  artifact-collaboration/
  education-domain/
  personalization-memory-analytics/
```

每个模块至少包含：

```text
domain/          纯领域对象与不变量
application/     用例与跨模块端口
infrastructure/  PostgreSQL、外部服务适配
api/             HTTP/事件入口适配
```

边界规则：

- 领域层不得 import Web、ORM、CloudBase、Netlify 或模型 SDK；
- 跨模块不能直接引用对方 infrastructure；
- 不能直接使用其他模块的 Repository；
- 跨模块读取使用显式 Query port；
- 跨模块修改使用目标模块 Command；
- DomainEvent 通过 Outbox 发布；
- 共享 `contracts` 只含 DTO、引用类型和协议，不放业务逻辑。

## 4.3 PostgreSQL Schema 基线

只采用一个数据库基线：

```text
一个 PostgreSQL 实例
├─ governance
├─ work
├─ runtime
├─ capability
├─ artifact
├─ education
└─ personalization
```

- 七个模块各自拥有独立 migration 目录和 migration ownership；
- 禁止跨 Schema 直接写入；
- Runtime 数据库角色只能写 `runtime.*`，可按最小字段读取获授权投影，不得写 `education.*`、`governance.*` 或 `personalization.*`；
- 跨模块变更必须调用目标模块应用服务；
- CloudBase Spike 若证明 Schema 管理不适用，必须新增 ADR 才能改用“单一 Schema + 强制前缀”fallback。

Gate 1A 保留 PGlite 作为快速 SQL 方言和 migration smoke test。
Gate 1B 已使用 Docker Compose、官方 `postgres:18` 和本机
`127.0.0.1:55432` 完成真实事务、并发、Outbox、连接池与低权限角色
验证。本机原生 PostgreSQL 不属于测试依赖链。

# 6. Gate 1A：平台骨架与无 LLM Walking Skeleton

## 目标

先证明平台边界、写入治理和运行归属成立，不在同一 Gate 中实现 Education Domain。

## 实现范围

### 七模块与 Contracts

- 七个模块目录和公共端口；
- 五类 Ingress 判别联合：Query、Command、DomainEvent、ObservationEvent、WorkflowSignal；
- `TenantContext`；
- `ActingContext`；
- `AuthorizationDecision`；
- formal write metadata：actor、purpose、owner、idempotency key；
- architecture fitness tests。

### 最小运行对象

- `QueryRun`；
- 最小独立 `Task` 与 `TaskRun`；
- `AgentRun`，且必须绑定 QueryRun 或 TaskRun；
- `ArtifactRevision`；
- `OutboxRecord`；
- `AuditRecord`。

Gate 1A 不实现 Case/Goal 层级和 Education 聚合。Task 可以独立存在。

### Capability 与 Runtime

- `MockModelProvider`，只返回确定性 fixture；
- `FakeTool`，声明 read/write 风险、输入输出和幂等属性；
- Runtime 只能通过 Capability port 运行 Mock/Fake；
- ContextManifest 最小引用；
- 输出 Schema 校验和 fail-closed。

### PostgreSQL 基础

- 七个 PostgreSQL Schema；
- 七个模块独立 migration ownership；
- 最小表、Outbox 和 Audit migration；
- 数据库角色与 GRANT/REVOKE 基线；
- 禁止跨 Schema 直接写入；
- Runtime 无权写入 Education、Governance、Personalization 正式表。

## 无 LLM Walking Skeleton

```text
CommandEnvelope
→ ActingContext / TenantContext
→ AuthorizationDecision
→ idempotency reservation
→ 独立 Task + TaskRun
→ AgentRun
→ MockModelProvider + FakeTool
→ ArtifactRevision
→ OutboxRecord
→ AuditRecord
→ response

QueryEnvelope
→ AuthorizationDecision
→ QueryRun
→ 读取 ArtifactRevision
→ response
```

`DomainEvent` 只允许从已提交写入的 Outbox 重放；`ObservationEvent` 在 Gate 1A 只进入候选接收端，不触发 Agent；`WorkflowSignal` 在没有目标实例时必须拒绝。

## 自动测试

- 七模块依赖方向和禁止 import；
- 五类 Ingress Schema；
- actor/purpose/owner/idempotency key 缺一即拒绝正式写入；
- 相同 Command 重放不产生重复 Task、Run、Artifact、Outbox 或 Audit；
- AgentRun 不得成为孤儿；
- Runtime 不得 import Education/Governance/Personalization repository；
- Runtime 数据库角色不得拥有这些 Schema 的写权限；
- PostgreSQL migration ownership 和跨 Schema SQL lint；
- DomainEvent、ObservationEvent、WorkflowSignal 路由隔离；
- 无 LLM 端到端 Walking Skeleton。

## 退出标准

1. workspace 的安装、类型检查、构建和测试可重复；
2. 无网络、无云服务、无真实模型仍可完成 Command 与 Query 闭环；
3. 所有正式写入都有 actor、purpose、owner、idempotency key 和 Audit；
4. 相同 idempotency key 重放只返回原结果；
5. Runtime 没有写入 Education、Governance、Personalization 正式表的应用端口或数据库权限；
6. 所有 architecture fitness tests 通过；
7. 在首次 push 前向用户报告，不连接远程。

## 预计

5～8 个专注开发日。

# 8. Gate 2：Teacher Copilot

## 目标

验证 AI 是否能成为教师可控、可解释的认知助手，而不是自动修改教学事实的流程机器人。

## 实现范围

- 教师工作台；
- Case/Goal/Task 页面；
- Evidence 列表、来源、时间、Assistance 和未知项；
- ContextManifest 可解释视图；
- `PedagogicalSuggestion`；
- `TeachingPlan` ContentArtifact 与 Diff；
- `SuggestionDisposition`；
- Mock/DeepSeek Provider 切换；
- PromptBundle、输出 Schema 和 Eval fixtures；
- 失败、超时、预算耗尽和人工接管 UI。

## 核心场景

教师提出：

> 根据三班最近的合成作业证据，调整明天一次函数课的重点；给出两种策略、各自依据和不适用条件，并形成可编辑教案差异。

Runtime 必须：

1. 只读取已授权字段；
2. 区分正式 Evidence、Estimate 和缺失证据；
3. 不把没有 Opportunity 的学生描述为能力不足；
4. 引用 EvidenceRef；
5. 提供至少一个替代方案；
6. 形成 Proposal 与 Diff；
7. 等教师处置；
8. 不写 ObservedPedagogicalMove。

## 评测

固定 30～50 个合成用例，包括：

- 证据充分、冲突、过期和缺失；
- AI 帮助程度不同；
- Opportunity 不可及；
- Prompt 注入材料；
- 请求读取无权访问学生；
- 请求直接向家长承诺；
- 请求把 Estimate 改成事实；
- 模型输出 Schema 错误；
- 模型超时。

## 退出标准

- 100% AgentRun 绑定 Run、Contract、Prompt 和模型版本；
- 100% 正式写入通过应用服务和授权；
- 0 个测试允许跨 learner/tenant 泄露；
- 所有失败路径不产生半发布 Artifact；
- 真实模型结构化输出首轮通过率目标不低于 95%；经受控修复后仍失败必须 fail closed；
- 教师可以查看每条建议的来源、未知项、模型贡献和撤销入口；
- Mock 与真实 Provider 通过同一合约测试。

## 预计

4～6 个专注开发日。

# 9. Gate 3：引导式个别学习

## 目标

验证系统是否能在不固化学生、不代替学生思考的前提下提供情境化支持，并形成可解释 Evidence。

## 实现范围

- `individual` Participation 模式；
- LearningInteractionProfile 发布与解析；
- 提示层级、答案释放和教师接管；
- Attempt；
- AssistanceContext；
- OpportunityOffer 和 LearnerOpportunityEvent；
- Observation/Evidence 候选；
- LearnerStateEstimate 的置信度、有效期和证据缺口；
- AI contribution attribution；
- 学生与教师可见范围。

## 关键故障用例

1. 学生未获得机会；
2. 学习材料不可访问；
3. 学生看到了高强度提示；
4. AI 给出了关键步骤；
5. 小组结果误送到 individual 模式；
6. 过期 Evidence 与新 Evidence 冲突；
7. 模型试图突破答案释放上限；
8. 学生请求查看其他学生信息。

## 退出标准

- 未提供或不可及 Opportunity 时 Estimate 保持 unknown；
- AssistanceContext 在所有 Evidence 路径中可回溯；
- AI 贡献不计为独立学生能力；
- 超出已解析契约的模型输出被拦截；
- 未实现的 small_group/whole_class 模式 fail closed；
- 教师可以修正或撤销 Evidence 候选；
- Profile 不出现“天生不适合”“能力差”等永久标签。

## 预计

4～6 个专注开发日。

---

# 10. Gate 4：教师长期连续性与最小个性化

## 目标

证明平台不只是一次 Task 工具，同时避免把长期连续性实现成持有权限的常驻 Agent。

## 实现范围

### Goal/Case

- 一个可独立存在的教师个人 Goal；
- 一个 `TeachingImprovementCase`；
- Goal 可通过显式关系关联 Case，但不强制属于 Case；
- Goal 进展由 Evidence/Task 投影；
- Task 可独立存在，也可结束而 Goal/Case 持续；
- 一个 `WorkflowInstance` 独立处理人工审批等待。

第一轮不实现完整 `StudentSupportCase`。引导式个别学习可以展示学生 Evidence，但不因此建立长期学生支持 Case。

### Personal Assistant Shell

Shell 只聚合引用和连续性视图：

- Preference；
- MemoryEntry；
- Active Case/Goal；
- Lens；
- 最近 ContinuitySnapshot。

每次智能任务仍创建短生命周期 Task Coordinator。Shell 不拥有权限、不直接调用 Tool、不保存教育正式状态。

### Memory

仅实现：

- 一条可审查、可修改、可删除的 `Reflective MemoryEntry`；
- 一条 `ProceduralSummary Candidate`，不得发布或直接执行；
- 一组教师明确设置的 Preference。

运行时按 scope、purpose、权限、新鲜度和预算生成 Memory View；删除 MemoryEntry 后，新 Run 不得继续召回。

### 个性化

- A 级：界面布局、格式和表达 Preference；
- B 级：只保留 ProceduralSummary Candidate，不进入 Published Context；
- C 级：本 Gate 不实现。

## 退出标准

- 新 Task 能恢复 Goal 与用户偏好，但不继承旧授权；
- 删除或更正 MemoryEntry 后，下一次 ContextManifest 可观察到变化；
- Shell 被停用不影响正式 Case/Goal/Task 数据；
- ProceduralSummary Candidate 不进入 Published Context；
- Workflow 等待恢复后，Task 投影正确；
- Candidate 不能直接执行 Tool；
- 没有 StudentSupportCase 或 C 级自动化路径。

## 预计

3～5 个专注开发日。

---

# 11. Gate 5：部署、演示加固与教师验收

## 目标

让远程教师能稳定、安全地完成完整演示，并将反馈转化为 v0.4 证据。

## 执行顺序

1. GitHub 远程仓库和分支检查；
2. secret scan、测试和构建；
3. 创建 Netlify Deploy Preview；
4. 验证前端路由、环境变量和回滚；
5. 经用户授权创建 CloudBase 环境；
6. 验证 PostgreSQL 模式、函数时限、连接数、CORS 和日志；
7. 部署受限 Demo API；
8. 设置访问码、速率和模型预算；
9. 在 Preview 完整验收；
10. 用户确认后，将现有 Netlify 站点关联到新仓库或提升经过验证的站点；
11. 邀请 1～3 位教师按脚本操作；
12. 收集观察、访谈和系统指标。

## 教师验收脚本

教师在没有架构解释的情况下完成：

1. 登录演示；
2. 找到一个持续中的教学改进 Goal；
3. 判断系统使用了哪些 Evidence、哪些未知；
4. 生成两种教学调整建议；
5. 修改 TeachingPlan Diff；
6. 接受其中一部分并拒绝另一部分；
7. 查看系统没有把“接受”当作“已实施”；
8. 查看一个学生 Attempt 的 AssistanceContext；
9. 纠正一条 MemoryEntry 或 Evidence 候选；
10. 找到撤销、关闭自动化和查看审计的入口。

## 验收指标

### 架构正确性

- 100% 正式写入有状态所有者、授权决策和来源；
- 100% AgentRun 绑定 QueryRun/TaskRun 与不可变互动契约；
- 100% Workflow 等待由 WorkflowInstance 持有；
- 重放测试不产生重复副作用；
- 0 条 C 级个性化自动生效；
- 0 个真实个人数据字段。

### 模型与性能

- 确定性 API 的本地 P95 目标小于 300ms；
- 不含模型的主要页面交互目标小于 2s；
- 模型请求采用明确的客户端超时、服务端 deadline 和取消状态；
- 真实模型失败时保留草稿前状态，并可切回 Mock；
- 每个场景记录 Token、延迟和预算，不以调用次数作为智能化指标。

### 教师体验

- 教师能区分 Evidence、Estimate 和 AI 建议；
- 教师能在不阅读技术文档的情况下修改和撤销建议；
- 教师能说出系统使用数据的原因和范围；
- 记录完成时间、犹豫点、误解和接管行为，但不把“点击率”单独作为成功指标。

## 预计

2.5～4.5 个专注开发日，另加教师可用时间。

# 12. 必做 Spike

| Spike | 验证什么 | 最小实验 | 成功标准 | 失败后的调整 |
|---|---|---|---|---|
| S-01 模块依赖 | 模块化单体能否防止越界写入 | 建七模块空壳、依赖规则和跨模块测试 | 非法 import/Repository 访问在 CI 失败 | 合并过细 package，但不放弃状态所有权 |
| S-02 Run 归属 | QueryRun、TaskRun、AgentRun 是否清晰 | 同一 UI 分别执行确定性 Query、AI Query、Task | 无孤儿 AgentRun；UI 状态不依赖 Agent 私有状态 | 简化 Run 字段，不合并真值源 |
| S-03 Contract 强制 | 互动契约是否真正限制模型 | 构造越级提示、泄露、答案释放测试 | 超界输出被确定性拦截 | 缩小首轮自适应范围，增加规则执行器 |
| S-04 Evidence lineage | 教师能否理解建议依据 | 从建议点击回到 Evidence/Attempt/Opportunity/Assistance | 所有建议都能回溯或明确标注“无足够证据” | 限制生成类型，先做证据选择 UI |
| S-05 Opportunity | 缺机会是否会被误判 | 四条 offered/access/barrier/not_observed 轨迹 | 后三种语义不被压成单一“未完成” | 暂停 Estimate 更新，只显示证据缺口 |
| S-06 Shell continuity | 长期连续性是否需要常驻 Agent | 两个任务之间恢复 Goal/Memory，但重新授权 | 连续且不继承旧 access 决策 | 缩小 Shell 为索引投影 |
| S-07 Memory 召回 | MemoryEntry 是否有用且可控 | 新增、修正、删除条目后重复同类 Task | Context 可解释变化；删除立即影响新 Run | 首轮只保留显式 Preference |
| S-08 Suggestion 语义 | 接受建议是否被误作现实事实 | 接受后不确认实施 | 无 ObservedMove；只存在 Disposition/Task | 将 ObservedMove 完全推迟 |
| S-09 CloudBase 适配 | Serverless 是否满足 Demo | 健康检查、PG 事务、函数超时、并发、冷启动 | 演示负载稳定；失败可恢复 | Demo 后端改用另一受管容器；不立即上 VM |
| S-10 Netlify 联接 | Preview、路由和 API 是否稳定 | 新仓库 Preview + 回滚 | 不影响现有站点；刷新与 CORS 正常 | 保留独立演示站点，不改现有站点 |

# 13. 风险与控制

| 风险 | 早期信号 | 控制 | 停止条件 |
|---|---|---|---|
| 演示变成功能堆砌 | 页面增加但核心链路不完整 | 只接受两个 Slice 内需求 | Gate 1A/1B 未过不得扩页 |
| 模块化单体退化为共享数据库脚本 | 跨模块直接 Repository 写入 | 依赖测试、迁移所有者、应用服务端口 | 任一正式写入无 owner |
| LLM 成为业务状态机 | Prompt 决定 Task/Workflow 真值 | 状态机确定性实现，LLM 只产草稿/计划 | 模型输出可直接改正式状态 |
| 个性化固化学生 | 一次行为形成长期标签 | 时效、不确定性、Opportunity/Assistance、C 级门 | 无法解释或撤销推断 |
| 密钥泄露 | secret 出现在 Git、日志或前端 | 轮换、secret scan、后端调用 | 已暴露密钥仍在用 |
| 公开演示被滥用 | 模型调用或 API 激增 | 访问码、限流、预算、合成数据 | 无法限制访问或费用 |
| CloudBase 产品约束不符 | 超时、连接、地域或配额失败 | S-09 在生产站点切换前完成 | 需要依赖未验证的固定时限 |
| Netlify 覆盖现有站点 | 关联仓库后旧站点不可恢复 | Preview、保存配置、确认后切换 | 无可验证回滚 |
| 教师误解 AI 建议为事实 | UI 混用状态和颜色 | 明确对象类型、来源和处置 | 教师无法区分 Evidence/Estimate/Suggestion |
| 合成数据过于理想 | 所有建议都正确 | 加入冲突、缺失、过期和帮助污染 | 只能演示“完美数据” |

# 16. v0.4 的进入条件

只有满足以下条件才开始编写 v0.4：

2. 六项勘误都在代码或测试中得到证明；

7. 能明确列出哪些 ADR 被验证、被否证或需要修订。

v0.4 应是“工程和教师证据驱动的架构收敛”，不是在 v0.3.2 上继续增加概念。

# 17. 第一轮完成定义

第一轮完成不是“网站能够打开”，而是同时满足：

- 教师可以操作两个纵向切片；
- 无 LLM 时系统仍有完整、可测试的业务闭环；
- 有 LLM 时模型被 Contract、Schema、权限和预算约束；
- Case/Goal 提供跨 Task 连续性；
- Personal Assistant Shell 提供个人连续性但不越权；
- Evidence、Opportunity、Assistance 和 Suggestion 语义没有被压扁；
- 所有数据均为合成数据；
- 访问、密钥、日志和成本有最低控制；
- GitHub、Preview、Demo 和回滚路径可重复；
- 教师反馈能够直接转化为 v0.4 的保留、修订或删除决定。
